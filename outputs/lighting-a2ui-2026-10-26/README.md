# 照明智能体：六个查询场景与 A2UI 交互设计

日期：2026-10-26。主要用户：个人值班、运行分析人员。交付：[可点击页面原型](index.html)。

## 设计结论

以自然对话作为入口，查完先回答“有没有问题、哪些值得看、依据是什么”，需要筛选、选对象和追查时再出现交互。复杂清单放入现有 Workbench，点击对象后展开证据。一次查询不变成一个需要管理的任务。

原型提供六个场景、四种能耗视图、设备详情、同回路对比、查询参数采集、当前示例清单 CSV 下载，以及失败、无记录、部分证据缺失状态。它是独立的 HTML 设计产物，不是已经接入生产技能的功能页面。

## 依据与读取范围

已通过既有授权连接，只读查看照明智能体技能目录中相关技能说明，以及单灯、RTU 两个固定报告模板。

没有执行技能中的 SQL、查询生产业务数据、控制设备或改写服务器文件。原型中的道路、设备、时间线、数值、诊断结论全部为合成示例。技能文件中记录的历史异常对象和历史筛查数字，没有当成本次查询结果。

## 页面组织

桌面保留三层清晰关系：窄侧栏用于切换演示场景，聊天列保留问题、结论和追问，结果区显示统计与清单。设备证据用右侧详情展开。场景侧栏是原型的演示导航；正式产品仍从现有对话入口进入，不能再给用户建立六个独立任务入口。

手机优先显示一句话结论、关键指标和异常列表，聊天按需打开，底部始终能继续提问。宽表格局部横向滚动，长设备标识不能把整页撑宽。

首屏不放大幅功能介绍、装饰性大数字背景、重复说明、空地图、默认展开的长报告或执行计划。报告与统计口径按需查看。

## 场景一：查整晚单灯运行

**典型提问**：“昨晚到今天早上，单灯运行怎么样？”

**需要回答**：整夜是否有大范围异常？哪些对象值得先查？能耗和亮灯时长是否自洽？

首屏展示：

- 明确的跨日时间窗、时区和统计生成时间。
- 夜间有有效巡测的灯数 / 纳管灯数，夜间无记录数，截止时点未解除报警数，夜间能耗。
- 按小时的报警分布和重点单灯清单。
- 重点对象的道路、单灯、RTU / 回路、亮灯分钟、额定功率、耗电与异常线索。

不能把“整夜有过样本”命名成“整晚在线率”，也不能把它直接填入 07:00 在线数。若需要在线率或亮灯率，必须取得现有系统口径与对应分母。

**交互链**：提问 → 简明结论 → 点击异常单灯 → 目标时点历史证据 → 同杆 / 同回路 → 必要时补上游 RTU → 回到对话继续问。

后续按钮建议：“只看未解除报警”“看看上游 RTU”“继续看夜间能耗”。只负责查询，不夹带消警或控制。

**对应技能**：`single-lamp-operation-report`；缺字段时按 `night-operation-analysis-with-fallback-sources` 的已说明路径补证据。完整报告仍遵守固定章节，紧凑界面只是摘要与导航，不替换正式模板。

## 场景二：查单灯报警，追到具体层级

**典型提问**：“昨晚哪些报警还没解除？”“这批灯是不是同一个回路的问题？”

首屏分别统计报警事件数、受影响去重单灯数、截止时点已解除数和未解除数。默认清单筛选为未解除，允许切回全部或查看频繁触发对象。

表格字段：单灯 / 灯杆、道路、RTU 与回路、报警类型、首次与最后触发时间、触发次数、截止时点恢复状态、证据入口。正式接口最好同时返回报警事件 ID，避免把同灯多次独立触发合并丢失。

点击对象后展示：

1. 报警时点和默认前后各 10 分钟的历史窗口。
2. 目标灯是“有记录但值异常”还是“应有记录却无记录”。
3. 同杆、同控、同回路的同步情况。
4. 必要时补同窗口的 RTU 供电与报警。
5. 结论层级、证据、排除项和缺口。

诊断收口沿用现有技能，只使用“更像单灯 / 单杆 / 同回路批量 / 控制箱或 RTU 上游 / 计划边界或报表口径问题”，或“证据不足，暂不能定性”。

重复触发不直接解释为重复入库；多次“触发→恢复→再触发”要作为事件链保留。贴近开关灯边界也不能直接判为误报。

**A2UI 动作**：“只看未解除”“比较同回路”“核对同一时段 RTU”“调整分析窗口”。动作携带设备与时间，不只回传一段脱离上下文的按钮文字。

**对应技能**：固定报警汇总继续由 `single-lamp-operation-report` 提供；需要解释原因时进入 `single-lamp-alarm-analysis`，批量集中时进入 `alarm-batch-pattern-diagnosis`。不因只看未解除而另建一套报告模板。

## 场景三：查 RTU 运行

**典型提问**：“RTU 昨晚运行怎么样？”“哪些整晚没上报？”

首屏：在管 RTU、截止时点命中现有有效上报 / 在线口径的台数、其余待核查台数、未解除 RTU 报警数。清单分开表达“上报过期”“整个窗口无记录”“巡测失败”，不能都叫通信故障。

表格字段：RTU 编号与名称、最后历史上报时间、判定时点和状态、支路数、关联异常单灯数。未知影响范围显示未知。

详情展示末次样本的 A/B/C 相电压电流，以及按需查询的回路状态、历史上报时间线和关联报警。能上报不代表供电和支路正常。

**交互链**：筛选待核查 → 打开 RTU → 核对历史上报与电参 → 这台 RTU 的夜间报警 / 下游单灯。

数据来源按 `rtu-operation-report` 固定使用 `sl.r_his_coplog_phase`，不把实时缓存 `sl.r_coplog_phase` 当作历史报告依据。默认采用系统已有在线判定；缺少判定配置时返回无法判定，不自创生产阈值。

原型中的“10 分钟内成功上报”是明确标注的演示参数，尚未核实为生产规则。

## 场景四：查 RTU 报警与受影响单灯

**典型提问**：“昨晚 RTU 报警主要是什么？”“缺相和漏电影响了哪些灯？”

首屏：报警事件数、受影响 RTU 去重数、截止时点未解除数和已解除数。清单按需要核对的电气风险展示，不把建议顺序伪装成系统已配置的告警等级。

表格字段：RTU、报警类型、相位 / 支路、发生和恢复时间、原始读数摘要、恢复状态、影响范围、历史证据入口。读数和阈值都要带单位。

点击报警后，围绕该报警前后窗口展示分相电参、同 RTU 其他回路、下游异常单灯及缺失证据。没有返回的阈值不补成通用常量。

详情页按专项技能给出不同核查面板，而不是把所有报警都套成同一张通用卡：

| 报警 | 应展示的专项证据与分支 |
| --- | --- |
| 支路漏电 | 原始单位与换算值、是否进入 `>1 A` 分支、自动断电结果、闭锁保护、断电后有效采样。`≤1 A` 仍不能判断安全；没有动作记录不当成动作失败。 |
| 电源缺相 | 昼夜、报警相位与回路对应、同事件相电流和回路电流、关联断路报警。不能只凭 `0 V` 完成整个诊断。 |
| 分相过流 | 当天与前两日同一时段曲线、已确认的曲线一致性标准、回路额定电流与实际值、相对额定的超出比例。额定值缺失时不计算“高 20%”。 |
| 回路断路 | 先确认亮化灯还是道路灯，再核对连续电流是否“小于 3 A 且频繁波动”、报警前电流及对应总电流。亮化灯路径结束不等于正常。 |

原型的断路详情可以选择“如果是亮化灯 / 普通道路灯”查看不同排查路径；正式接入适合用 A2UI 收集该缺失参数。分支阈值来自现有技能，不是由原型新增的现场保护定值。

**A2UI 动作**：“只看未解除”“只看电气类”“看关联下游灯”“核查同一时段电参”。从报警进入下游查询时携带 RTU、相位 / 回路、报警 ID 和时间锚点。

**技能组合**：`rtu-operation-report` 提供总体统计；缺相、分相过流、支路断路和漏电分别沿用已有专项技能。运行报告与原因分析共用证据，但不把“收到报警”等同于“原因已确认”。

不在此页面加入一键重启、强制开灯、消警、调整阈值等控制行为。

## 场景五：查能耗、解释波动与节能率

能耗查询拆成四种明确口径，用用户切换来决定查询，不把不同时间基础拼在一张趋势图里。

| 视图 | 典型提问 | 主要展示 | 技能 |
| --- | --- | --- | --- |
| 昨夜同窗口 | “昨晚比前晚多用了多少电？” | 两夜 18:00–07:00 总耗电、同批灯亮灯时长、时长贡献与非时长贡献、高低值重点灯 | `diagnose-energy-spike-by-duration-decomposition`、夜间分析技能 |
| 近 7 日日报 | “最近一周能耗趋势？” | 前 7 个完整自然日、总耗电、日均、逐日变化；点击日期继续追查 | 已有日报与只读查询流程 |
| 30 日异常波动 | “哪些 RTU 用电突然增加？” | RTU + 日期点、当日 / 前日 kWh、变化量、变化率、覆盖和剔除情况 | `rtu-energy-anomaly-screening` |
| 7 日节能率 | “节能率多少，记录是否一致？” | 总理论 / 实际能耗、加权节能率、系统记录值与计算值、是否取得目标 | `smartlight-energy-saving-rate-analysis` |

夜间对比至少同时保留总能耗、可比样本覆盖、亮灯时长、额定功率与实际功率证据。高能耗不直接等于故障，低能耗不直接等于节能。

时长拆分建议逐灯完成：

```text
时长贡献_i = 前夜能耗_i / 前夜亮灯小时_i × (本夜亮灯小时_i − 前夜亮灯小时_i)
非时长贡献_i = 本夜能耗_i − 前夜能耗_i − 时长贡献_i
```

仅计算两夜都有有效记录且基准时长大于 0 的同一批灯。未匹配对象、零基准时长、样本外差额和残差分别披露，不能把同一批样本的拆分直接冒充全网完整解释。

高低值清单保留“耗电、分钟、额定功率”。现有单灯报告的长时低耗筛查为“亮灯 >500 分钟且耗电 <0.1 kWh”，这里只作为待核查线索。

RTU 上升波动筛查沿用现有固定双阈值：增加 ≥50 kWh 且相对前日增加 ≥30%。若要纳入下降，另走对应分析或先明确变更口径；不在界面里默默改成绝对变化。

7 日 RTU 汇总保留技能规定的大值过滤，并说明剔除数量。前日为 0、缺失、复位或无效记录时，不计算无效环比。

综合节能率先汇总理论与实际能耗，再计算 `(Σ理论 − Σ实际) / Σ理论`，不平均每日百分比。系统节能率为 0 但计算值非零，只标为指标一致性异常；未提供目标时，不输出达标结论。

## 场景六：单灯合计与 RTU 能耗对账

**典型提问**：“单灯合计怎么比 RTU 上报还高？”“哪些 RTU 出现倒挂？”

默认昨日自然日 D 日报。首屏分别显示可比较的倒挂 RTU 数、缺少日报的 RTU 数、可比较差额合计与比值可计算数。

主表沿用技能字段：日期、RTU 编号与名称、有单灯能耗的灯杆数与灯源数、单灯能耗合计、RTU 日报、差额、比值。按超出 kWh 降序，缺失另列。

点击 RTU → 按回路分组 → 查看单灯明细与台账覆盖 → 核对抄表时刻与挂载关系。优先回答差额来自哪些对象，不直接给“真实耗电异常”的定论。

主关联链路必须保持现有技能的约束：

```text
l_energy_report.alone_lamp_id
→ l_alonelamp.alone_lamp_id
→ l_alonelamp.rtu_road_id
→ r_rturoad.rturoad_id
→ r_rturoad.road_switch_id
→ r_road_switch.road_switch_id
→ r_road_switch.control_cabinet_id
→ r_rtu.control_cabinet_id
```

不能用灯杆变压器关系直接替代主链路。过滤沿用 RTU `0 ≤ kWh <1500`、单灯 `0 ≤ kWh <100`、`report_type='D'`，并披露过滤和覆盖数。

三种边界分开：RTU 有有效日报且为 0、RTU 日报缺失、日报被判无效。单灯为正且 RTU 有效为 0 仍可列倒挂，但比值不可计算；缺少 RTU 日报则不能参与倒挂判定。比值筛选只纳入可计算值。

**对应技能**：`rtu-lamp-energy-inversion-query`。固定归属验证不靠前端猜测，正式结果不能像原型那样按比例构造回路分项。

## A2UI 应该承担什么

服务器 `render-a2ui` 的当前规则已经规定：普通解释、查询结果、统计表格、诊断证据和报告继续使用 Markdown；当需要用户选择、确认、补参数和继续执行时，调用 `render_a2ui`。

因此建议按以下方式落地：

| 内容 / 动作 | 呈现与执行方式 |
| --- | --- |
| 一句话结论、事实、证据与完整报告 | 现有 Markdown 消息，不复制成一堆装饰卡 |
| 已返回数据内的清单搜索、筛选、详情展开 | 宿主本地交互，不为每次点击调用 LLM |
| 用户补设备范围、时间或选择下一步分析 | A2UI Basic Catalog 的输入、选项与按钮 |
| 新取历史证据、扩大到回路 / RTU | A2UI 动作回传智能体，复用业务技能与 SQL MCP |
| 图表 | 优先现有图表工具产物，经 `Image` 或宿主结果区展示 |
| 精细表格、联动时间线 | 本原型的 HTML 视觉设计；正式接入优先复用宿主已有 Markdown 表格与 Workbench，不声称 Basic Catalog 原生支持业务 Table / Chart |
| Word 成品 | 用户要求后调用已有报告交付与 Word 技能，保留固定章节与图表 |

需要用户反馈才能继续的交互按服务器技能使用 `wait_for_action=true`，默认超时 300 秒。只展示且不等待回传的内容用 `false`。到期显示“交互已过期，请重新发起”，不能把超时当成同意，也不能继续执行。已完成、取消、过期的历史卡片只读。

完整报告与界面视图分别承担阅读和分析操作，不能为了页面紧凑擅自删除正式报告章节。

## 动作应该保留的上下文

以下是建议的业务动作名和业务上下文，不是已经注册的工具、API、协议标准或可直接发送的 A2UI 消息。接入时映射到选定运行时的正式 Action 格式。

| 建议动作 | 必须带回的上下文 |
| --- | --- |
| `lighting.query_night` | 项目 / 区域、设备范围、开始 / 结束、时区、统计口径 |
| `lighting.inspect_lamp` | 单灯 ID、报警事件 ID、时间锚点、历史证据窗 |
| `lighting.compare_circuit` | RTU / 回路 / 单灯归属、事件窗、计划边界、触发来源 |
| `lighting.inspect_rtu_alarm` | RTU、报警 ID、相位 / 回路、事件窗 |
| `lighting.decompose_energy` | 两个同口径窗口、可比样本规则、设备范围 |
| `lighting.reconcile_energy` | 自然日或逐日范围、日报类型、RTU、有效值过滤口径 |

服务端必须校验会话与查询范围权限、设备归属、时间和动作白名单，不能信任客户端传来的单灯→RTU 关系或已经计算好的总数。SQL 仍走受控只读入口；固定查询按原技能复用，新增或改变口径才按已有 SQL 确认规则处理。

例如，从“某条单灯报警”跳到“同回路”时，业务意图应至少包含：

```json
{
  "intent": "lighting.compare_circuit",
  "queryScope": {"rtuId": "RTU-017", "circuitId": "2"},
  "anchor": {"kind": "alarm", "alarmId": "demo-alarm-001", "at": "2026-10-25T18:24:00+08:00"},
  "window": {"start": "2026-10-25T18:14:00+08:00", "end": "2026-10-25T18:34:00+08:00"},
  "timezone": "Asia/Shanghai"
}
```

这个业务意图需要包装成目标协议接受的 Action，不能直接当作 wire payload 发给渲染器。

## 正式数据与状态要求

每块真实结果至少保留查询标识、设备范围、时间口径、数据截止时点、生成时点、来源、数据覆盖和缺失 / 过滤情况。历史证据另带自己的时间锚点与窗口。

| 情况 | 应有表现 |
| --- | --- |
