## 2. 固定格式要求

### 抬头区
- 第一行标题固定为：`# 单灯运行报告（<时间范围标题>）`
- 第二行标题固定为：`# 单灯运行报告`
- 第三行固定为：`报告时间范围：<开始时间> ~ <结束时间>`
- 第四行固定为：`统计生成时间：<生成时间>（Asia/Shanghai）`
- 第五行固定为：`数据范围：单灯报警历史表 l_his_hitch_alarm + <时点> 时点巡测表 l_coplog + 单灯能耗表 l_energy_report`

### 一级章节标题
固定为以下十个标题，编号、文字、顺序都不能改：
- `## 一、总体结论`
- `## 二、报警总览`
- `## 三、报警类型分布`
- `## 四、报警时间分布（按小时）`
- `## 五、重点道路分布`
- `## 六、重点异常单灯`
- `## 七、<时点> 时点单灯运行状态`
- `## 八、能耗情况分析`
- `## 九、建议处置顺序`


### 二级小节标题
固定保留：
- `### 道路观察`
- `### 未解除报警重点清单`
- `### 重点对象判断`
- `### 运行判断`
- `### 能耗分布`
- `### 能耗判断`

### 数据展示格式
- 总览区统一使用：`字段名：数值`
- 类型分布统一使用：`类型名：X 条，涉及 Y 盏灯，未解除 Z 条`
- 小时分布统一使用：`YYYY-MM-DD HH:00：X 条，Y 盏灯`
- 道路分布统一使用：`道路名：X 条，涉及 Y 盏灯`
- 重点异常单灯固定使用 Markdown 表格，列顺序为：`灯杆编码`、`单灯/灯源标识`、`道路名`、`报警数`、`首次报警时间`、`最后报警时间`、`报警类型`；不得改回逐行描述格式
- 未解除报警重点清单默认使用 Markdown 表格，建议字段至少包含：`灯杆编码`、`单灯/灯源标识`、`道路名`、`报警类型`、`首次时间`、`最后时间`
- 运行状态区统一使用：
  - `最新样本数：X`
  - `在线数：X`
  - `离线数：X`
  - `开灯数：X`
  - `关灯数：X`
- 能耗分析区统一使用：
  - `总耗电量：X kWh`
  - `有能耗记录单灯数：X`
  - `平均单灯耗电：X kWh/灯`
  - `平均亮灯时长：X 分钟`
  - `异常高能耗单灯数：X`
  - `异常低能耗单灯数：X`
- 能耗分布统一使用 Markdown 表格，建议字段至少包含：`类型`、`道路`、`灯杆/单灯`、`耗电量(kWh)`、`亮灯时长(分钟)`、`额定功率(W)`、`说明`

### 图表展示要求
- 图表是固定增强项，不单独占一级章节；应插入在对应数据章节之后。
- 默认优先保留以下图表位：
  - `## 三` 后：报警类型分布图
  - `## 四` 后：按小时报警分布图
  - `## 五` 后：重点道路报警 TopN 图
  - `## 八` 后：高能耗异常 TopN 图、低能耗异常 TopN 图
- 聊天正文可用 Markdown 图片；Word 成品优先插入实际图表图片。
- 若图表生成失败，可省略图片本体，但不得省略对应章节的数据与判断。

### 强调样式
- 结论段、观察段、判断段中的重点数值或重点对象，保持使用 `**加粗**`
- 非重点描述不随意加粗
- 中文标点风格保持一致，使用中文冒号、顿号、句号

### SQL 输出
- 默认报告正文不输出 SQL。
- 只有用户明确要求“附 SQL / 展示 SQL / 给我查询语句”时，才在正文最后追加：`## 十、用于本报告的核心 SQL`。
- 追加 SQL 时保留“核心 SQL”概念，不改名，并按实际使用顺序附上。

## 3. 标准生成流程

### 第 1 步：确定报告时间窗
- 默认按用户指定时间窗生成
- 若用户表达为“昨晚到今天早上 7 点”，统一解释为：前一日 `18:00:00` 到次日 `07:00:00`
- 同步生成标题时间范围文本与正文时间范围文本

### 第 2 步：提取报警总体统计
基于 `sl.l_his_hitch_alarm` 在时间窗内统计：
- 报警总数
- 涉及单灯数
- 涉及灯杆数
- 涉及道路数
- 已解除数（`alarm_state = 2`）
- 未解除数（`alarm_state IN (0,1)`）

### 第 3 步：提取报警类型分布
按报警类型聚合，输出：
- 类型名称
- 报警条数
- 涉及单灯数
- 未解除数

### 第 4 步：提取按小时的报警时间分布
按小时分桶统计：
- 每小时报警条数
- 每小时涉及单灯数

### 第 5 步：提取重点道路分布
按道路聚合，至少输出 Top N（通常前 10）：
- 道路名
- 报警条数
- 涉及单灯数

然后围绕以下逻辑生成“道路观察”：
- 头部道路是否集中
- 是否存在少量灯反复上报
- 是否存在报警数与灯数接近的一次性触发道路

### 第 6 步：提取重点异常单灯
按“灯杆 + 单灯序号 + 道路”维度聚合，输出：
- 对象名称
- 报警条数
- 首次报警时间
- 最后报警时间
- 报警类型组合

随后补充“未解除报警重点清单”，优先提取当前仍未解除且具备处置价值的对象，建议按末次发生时间倒序或持续时间倒序展示，输出：
- 灯杆编码
- 单灯序号或灯源标识
- 道路名
- 未解除报警类型
- 首次报警时间
- 最后报警时间

然后围绕以下逻辑生成“重点对象判断”：
- 单杆位/控制单元持续异常
- 同杆双灯同步异常
- 漏电相关对象优先现场排查
- 未解除存量对象是否集中在少数道路或少数设备

### 第 7 步：提取时点巡测运行状态
基于 `sl.l_coplog` 提取目标时点最新巡测快照，输出：
- 最新样本数
- 在线数
- 离线数
- 开灯数
- 关灯数

然后围绕以下逻辑生成“运行判断”：
- 是否属于日间熄灯后时点
- 关灯是否合理
- 离线数是否异常偏高
- 是否可能存在历史失联累计/快照口径问题
- 如需进一步判断，建议补充道路在线率、前后时点变化、重点灯源连续曲线

### 第 8 步：提取能耗情况分析
基于 `sl.l_energy_report`，必要时补充 `sl.l_his_coplog`，输出：
- 总耗电量
- 有能耗记录单灯数
- 平均单灯耗电
- 平均亮灯时长
- 异常高能耗单灯数
- 异常低能耗单灯数
- 重点高值/低值对象清单（默认用 Markdown 表格展示，并补充额定功率字段）

然后围绕以下逻辑生成“能耗判断”：
- 总能耗变化更像由亮灯时长变化驱动，还是由个别异常高值驱动
- 是否存在亮灯时长基本正常但能耗明显偏低的疑似异常单灯
- 是否存在亮灯时长不长但能耗明显偏高的疑似功率/计量异常单灯
- 是否存在额定功率与实测能耗明显不匹配、疑似台账配置错误或实际带载异常的对象
- 道路层面是否存在成片偏高或偏低现象

### 第 9 步：输出总体结论
总体结论固定为两段式压缩摘要，围绕：
- 整体报警量、涉及范围、未解除占比
- 主导报警类型
- 峰值时段及可能原因
- 能耗整体水平与异常对象特征

### 第 10 步：输出建议处置顺序
建议处置顺序固定围绕：
1. 先查集中爆发时点是否与策略、供电切换、通信波动相关
2. 再处理主导报警类型与头部重点道路
3. 再处理重复高频对象的单杆级专项排查
4. 再优先核查亮灯时长正常但能耗异常偏低/偏高的对象
5. 最后把漏电相关对象提为高优先级现场安全检查

### 第 11 步：按需附上核心 SQL
默认不附 SQL。只有用户明确要求“附 SQL / 展示 SQL / 给我查询语句”时，才将本次报告实际使用的核心 SQL 原样附在最后一节。

## 4. 生成时的硬约束

### 允许变化的部分
- 时间范围
- 统计数值
- 排名结果
- 具体道路名
- 具体灯杆/单灯对象
- 观察结论与判断内容中的事实描述
- 按需追加 SQL 时，核心 SQL 的筛选时间和必要字段
- 图表图片本体

### 禁止变化的部分
- 报告总标题写法
- 各章节标题名称
- 各章节顺序
- 各小节标题名称
- 各类行文的组织方式
- 总览/分布/重点对象/运行状态/能耗分析的字段排列方式
- SQL 放在最后这一要求

## 5. 默认聊天正文 / Word 附件落地规则

该技能的默认交付目标是**聊天正文**，不是企业微信文档。

执行要求：
- 报告生成完成后，默认先在聊天中返回正文
- 若用户要求“附件”“Word”“可转发成品”，则生成含图表的 Word 附件交付
- 若用户额外要求聊天内也展示正文，则在发送附件的同时保留正文或摘要
