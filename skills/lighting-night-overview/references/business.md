# 夜间报告时间窗口选择

## 何时使用

- 用户提到"昨晚到今早""昨天晚上到今天早上""昨夜运行情况"等夜间时间段
- 需要确定 SQL 查询的起止时间
- 不确定该用 18:00~06:00 还是 18:00~07:00

## 时间窗口规则

| 报告类型 | 开始时间 | 结束时间 | 说明 |
|---------|---------|---------|------|
| 单灯运行报告 | 前一日 18:00:00 | 当日 07:00:00 | “昨晚到今天早上7点”按 07:00 截止；需区分 07:00 后自然离线 |
| 单灯报警分析 | 前一日 18:00:00 | 当日 07:00:00 | 未解除报警与夜间事件默认覆盖到 07:00；用户明确到 06:00 时按 06:00 截止 |
| RTU 能耗分析 | 前一日 18:00:00 | 当日 07:00:00 | RTU 24 小时上报，关灯后仍有待机能耗，需覆盖到 07:00 |

## 步骤

1. **判断报告类型**
   - 涉及单灯巡测、亮灯时长、单灯报警 → 单灯类，默认用 18:00~07:00；用户明确“到 6 点”时用 18:00~06:00
   - 涉及 RTU 日用电量、RTU 能耗统计 → RTU 类，用 18:00~07:00
   - 若同时包含两种，在输出中分别标注各自时间窗口

2. **输出完整时间戳**
   - 格式：`YYYY-MM-DD HH:MM:SS ~ YYYY-MM-DD HH:MM:SS`
   - 必须写明完整日期和时间，避免歧义

3. **不要混用口径**
   - 单灯报告默认 07:00 截止，但分析 07:00 附近状态时必须说明白天关灯后不上电，不能把自然离线误判为故障
   - RTU 能耗不得使用 06:00 截止（会漏掉关灯后待机能耗）

# 夜间运行分析（含缺字段回退）

## 何时使用

- 用户要查“昨晚到今早”“昨天晚上到今天早上”的单灯运行情况
- 需要统一夜间口径，而不是按自然日白天统计
- 主表如 `l_lamp_online_rate` 缺少亮灯次数、亮灯时长等关键字段
- 需要判断单灯是否夜间异常，但要避免把白天未上电状态误判为故障

## 使用约束

- 时间窗默认统一为前一日 `18:00:00` 到次日 `07:00:00`；用户明确要求“到 6 点”时按 `06:00:00` 截止
- 生成或改写 SQL 时，只保留对 `AGENTS.md` / `sql-safe-query` 的短引用；具体确认流程按 `sql-safe-query` 执行
- 不猜字段；字段、schema、口径或方言不确定时，先走 `sql-safe-query` 的示例检索与 schema 确认流程
- SQL 查询结果获取优先走已配置 SQL 工具；本地文件说明可用 平台已加载的参考

## 步骤

1. 明确时间窗
   - 将“昨晚到今早”“昨天晚上到今天早上”默认解释为 `18:00~07:00`
   - 在输出中写清完整起止时间，避免被理解为自然日

2. 先确认主分析表是否具备关键字段
   - 检查目标表是否有亮灯次数、亮灯时长、在线率、能耗等指标
   - 若关键字段缺失，不继续硬套主表口径

3. 必要时回退数据源
   - 用 `sl.l_energy_report` 获取夜间能耗、可推断亮灯活跃度的指标
   - 用 `sl.l_his_coplog` 获取历史开关灯/巡测样本，补亮灯时长、时点状态、电压、功率等依据
   - 组合时优先按单灯主键和夜间窗口聚合后再判断

4. 交叉判断夜间运行情况
   - 先看夜间是否有能耗
   - 再看亮灯时长是否明显偏短
   - 再看巡测在线、电压、功率是否与亮灯状态自洽
   - 白天 `在线=0`、`电压=0`、`功率=0` 不能直接判异常；重点看夜间上电时段

5. 形成结论
   - 先给整体判断：是否整体稳定、是否存在大面积夜间离线或整网异常
   - 再列异常单灯：优先列亮灯时长明显偏短、能耗显著异常、夜间多指标不自洽的对象
   - 若某一时点全离线/全关灯，更先判断是否为熄灯后快照或统计口径效应，不直接下整网故障结论

## 输出格式

- 时间窗：`YYYY-MM-DD HH:MM:SS ~ YYYY-MM-DD HH:MM:SS`
- 整体结论：1 段
- 判断依据：3-5 条要点
- 异常单灯：列表，含单灯标识与异常原因
- SQL 正确性确认过程：仅简述是否做了示例检索、schema/字段确认、为何采用主表或回退表；默认不输出完整 SQL，只有用户明确要求“附 SQL / 展示 SQL / 给我查询语句”时才追加 SQL
