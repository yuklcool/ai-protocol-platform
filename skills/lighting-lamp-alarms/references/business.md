本文件保留源技能的业务核查规则；平台工具、默认交付和历史证据约束以当前 SKILL.md、runtime.md 为准。示例不是实时业务事实。

## 来源：single-lamp-alarm-analysis

# 单灯问题分析

用于分析以下场景：
- 单灯报警为什么发生
- 单灯为什么离线、掉线、异常亮灭
- 为什么报表把某灯或某杆记为离线

核心目标不是只看“当前状态”，而是围绕**目标时点**建立证据链，判断问题层级：
- 单灯问题
- 单杆问题
- 同回路批量异常
- 控制箱 / RTU / 上游问题
- 计划边界 / 报表口径问题
- 或证据不足

## 一、适用边界

适用于：
- 用户要判断问题更像单灯、单杆、同回路还是上游问题
- 用户要解释某次报警、离线、掉线、异常亮灭的原因层级
- 用户要解释为什么某灯或某杆被报表记为离线

不适用于：
- 只做固定模板成品报告的场景（优先用对应报告技能）
- 无需分析、只要简单统计列表的场景

## 二、必须遵守的规则

### 1. SQL 统一走安全确认流程
先读并遵守：
- `skills/sql-safe-query/SKILL.md`
- 涉及执行入口时，再读 `skills/sql-safe-query/references/runtime.md`

凡需生成、改写或补全 SQL，统一按以下顺序：
**明确目标 → 检索相似示例 → 核对真实 schema / 字段 → 生成只读 SQL → 执行查询**。

规则：
- 优先真实执行，不只给 SQL 草稿。
- 禁止猜表、猜字段、猜关联。
- 发现字段不存在、表结构不确定、方言不兼容时，必须先回退到 schema 校验。

### 2. 历史问题优先看历史证据
- 不要只拿当前实时状态解释历史报警。
- 先锁定报警时刻、离线时刻或报表业务日晚间窗口，再查历史巡测。
- 单灯历史主证据优先用：`sl.l_his_coplog`、`sl.r_his_coplog_phase`
- `sl.l_coplog`、`sl.r_coplog_phase` 仅作当前/末态补充，不作历史主证据。

### 3. 先定时间口径，再做分析
默认口径：
- 报警类：报警时刻前后 **10 分钟**
- 报表类：报表日期 D 对应 **D 日晚开灯到 D+1 日早关灯**
- 数据过稀可扩到 **30 分钟或整夜**；数据过密可缩到 **5 分钟**

特别注意：
- 单灯白天通常停报，白天无数据不能直接判故障。
- RTU 通常 24 小时上报，可作为上游参照。
- 不要把报表日期直接当自然日 `00:00~24:00`。

### 4. 结论必须落到明确层级
最终只能收口为以下之一：
- 更像单灯问题
- 更像单杆问题
- 更像同回路批量异常
- 更像控制箱 / RTU / 上游问题
- 更像计划边界 / 报表口径问题
- 证据不足，暂不能定性

### 5. 必须区分两类异常
- **异常值型**：有巡测，但在线、电压、电流、功率等异常
- **无记录型 / 失联型**：应有巡测时无任何记录，或末次停留在上一运行窗口

对“夜间应有巡测却整段无记录”的场景，优先归入无记录型；不要硬按异常值解释。

## 三、执行模式

### 快路径（默认）
适用于：
- 用户只想快速判断是单灯、单杆、同回路还是上游问题
- 只需先做初步归因
- 只需解释“为什么异常 / 为什么被报表算离线”

最小闭环：
1. 校准时间口径
2. 锁定目标报警时间或报表日期
3. 锁定目标归属
4. 判断是否命中开关灯计划边界
5. 查目标灯历史巡测
6. 查同回路历史巡测

若这几步已足够判断，就直接输出结论，不默认把所有步骤全查完。

### 完整路径（按需）
仅在以下情况继续补查：
- 快路径后仍无法区分层级
- 用户明确要求更细根因
- 已发现批量异常，需要 RTU 证据收口
- 需进一步区分单灯、单杆、控制器、杆内供电等层级

## 四、标准步骤

1. **锁定分析口径**：先判断是报警时点分析、报表业务日分析，还是当前末态分析。
2. **锁定目标对象**：查清报警类型、报警时间、灯杆/单灯、是否已解除、是最近一次还是历史反复。
3. **锁定资产归属**：至少锁定 `lamp_post_id`、`alone_lamp_id`、`transformer_id`、`alone_lamp_control_id`、`rtu_road_id`，可追到时再补 `rtu_id / rtu_code`。
4. **判断计划边界**：核对 RTU 支路开关灯计划与系统开关灯时间；若目标时间贴近 `on_time/off_time` 或系统开关灯时刻，先标记为计划边界时刻，但不能据此跳过后续证据。
5. **查目标灯历史巡测**：默认主查 `sl.l_his_coplog`，重点看在线、开灯、电压、电流、功率、功率因数、调光值、信号强度、是否有记录、首次/末次时间、是否恢复。
6. **查同杆 / 同控**：判断同杆有几盏灯、是否共用 `alone_lamp_control_id`、是否同步异常或同步无记录。
7. **查同控制箱（按需）**：当同回路判断还不够，或用户明确要求扩大范围时执行。
8. **查同回路历史巡测**：这是默认必做的横向对比步骤，用于区分目标灯局部异常和回路级异常。
9. **补 RTU 证据（按需）**：怀疑批量异常、控制箱或上游问题时，补查 RTU 历史巡测与 RTU 历史告警。
10. **收口结论**：回答问题发生时间、目标灯表现、同杆/同回路是否同步异常、RTU 是否有支持性证据，以及最终更像哪一层的问题。

详细判据、典型模式和 SQL 示例见：
- `references/diagnosis-patterns.md`
- `references/sql-snippets.md`

## 五、输出要求

不要只贴 SQL，也不要只给结论。
最终输出按下面结构组织：

1. **诊断总览**：用简表汇总候选层级，建议列为“排序 / 状态 / 检查项 / 当前判断 / 核心依据”。状态建议仅使用：`命中`、`可能相关`、`无法判断`、`已排除`。
2. **结论**：一句话明确收口，只能使用以下表述之一：
   - 更像单灯问题
   - 更像单杆问题
   - 更像同回路批量异常
   - 更像控制箱 / RTU / 上游问题
   - 更像计划边界 / 报表口径问题
   - 证据不足，暂不能定性
   可补充置信度：高 / 中 / 低。
3. **分析摘要**：用 3~6 条写清时间口径、目标灯关键表现、异常值型/无记录型、同杆/同回路情况、RTU 支持性证据、为何当前结论最成立。
4. **关键证据**：至少给出 3 类证据；如缺失需说明。
5. **排除项**：列出 2~4 条已排除层级及原因。
6. **下一步建议**：给 1~3 条建议，分数据侧 / 现场侧均可。
7. **SQL确认**：默认只简述已做的示例检索、Schema/字段确认与只读执行验证；不输出完整 SQL。只有用户明确要求“附 SQL / 展示 SQL / 给我查询语句”时，才按实际执行步骤列出完整 SQL，只列本次实际执行部分。
8. **说明**：只写一段，说明时间窗口口径、证据缺口，以及哪些是事实、哪些是“现有数据更支持”的判断。

## 六、最小快路径要求

如果用户只要快速判断“单灯还是批量”，至少完成：
1. 锁定时间口径
2. 锁定时间锚点
3. 锁定归属
4. 查计划边界
5. 查目标灯历史巡测
6. 查同回路历史巡测

若这几步已显示同回路多灯同步异常，可先给初步结论；需要更稳时再补 RTU 证据。

快路径输出时：
- 保留诊断总览
- 先给一句结论
- 只保留最关键证据
- SQL 只列本次实际执行部分

## 七、硬性警告

- 不要把当前实时状态直接当历史报警原因。
- 不要把报表日期默认当自然日 `00:00~24:00`。
- 不要把上一夜凌晨巡测误当成当日晚间运行证据。
- 不要把 RTU 的 24 小时连续上报习惯套到单灯上。
- 不要把单灯白天停报窗口内的无记录直接判故障。
- 不要只凭关灯、功率 0、无后续上报就判故障，必须结合计划边界、同回路和 RTU 证据。
- 不要看到整段无巡测还按异常值型解释，应先判断是否无记录型。
- 不要看到单灯报警就直接下“单灯坏了”的结论，必须至少做一次同回路横向比对。
- 不要看到 RTU 有历史通信失败就默认本次也是通信问题，必须核对时间是否对齐。
- 不要省略时间窗口。
- 不要只给结论不给证据。
- 若证据不足，明确写：**证据不足，暂不能定性**。
