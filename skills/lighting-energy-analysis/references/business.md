# Diagnose Energy Spike By Duration Decomposition

## 何时使用

- 用户要求解释某一天总能耗为什么异常偏高。
- 需要判断主因是亮灯时长变长，还是功率、计量、台账异常。
- 需要区分“全网普遍多亮”与“少数高值点拉高峰值”。
- 需要给出可继续落地排查的下一步线索。


## SQL 生成提醒

- 本技能涉及生成、改写或补全 SQL 时，默认统一遵循 `sql-safe-query` 口径：**先明确查询目标 → 检索相似示例 → 核对真实 schema / 字段 → 生成只读 SQL → 执行查询**。
- 优先复用 `skills/sql-safe-query/SKILL.md` 中的检索、Schema 约束和安全执行约定，再按本技能目标补充逐灯对比、聚合和筛查逻辑。
- 这样可以避免把模板假设字段直接写死，出现 `sl.l_alonelamp.lampnum` 不存在、`sl.l_coplog.create_date` 不存在这类“真实字段与模板假设不一致”的报错。
- 按当前工作区约束，遇到这类情况不能猜字段；必须先回到 `sql-safe-query` 的检索结果，或先做真实 Schema 校验后再继续。
- 若本技能已有经过验证的固定 SQL，可直接复用；但只要出现字段不存在、表结构不确定、方言不兼容、统计口径变化、关联关系不确定或新增分析维度，**按 `AGENTS.md` 中的 `sql-safe-query` 标准确认流程重新确认**。
## 核心指标

分析日能耗异常时，优先联合查看：
- 总能耗
- 户均能耗
- 总亮灯分钟
- 户均亮灯分钟
- 上线率
- 亮灯率
- 报警
- 高值单灯明细

## 标准步骤

### 1. 先看全局是否真的异常

至少对比异常日前后几天：
- 总能耗
- 户均能耗
- 总亮灯分钟
- 户均亮灯分钟
- 上线率与亮灯率
- 报警量或未解除报警情况

目的：先判断异常更像全局行为变化，还是故障导致的局部偏差。

### 2. 做相邻两日逐灯对比

以异常日和前一日为主。

逐灯对比至少保留：
- 两日能耗
- 两日亮灯分钟
- 能耗增量
- 亮灯分钟增量

若需要，可补充灯杆、道路、RTU 等定位字段，便于后续追查。

### 3. 拆分能耗增量来源

将逐灯能耗增量拆成两部分：
- 亮灯时长增加贡献
- 非时长增加贡献

用途：
- 若大部分增量来自时长增加，说明高能耗主要由多亮、更久亮驱动。
- 若非时长贡献很高，再提高对功率、计量、台账或带载异常的关注。

### 4. 计算“每亮灯小时能耗”

对异常日前后日期计算：
- 总能耗 / 总亮灯小时
- 或户均能耗 / 户均亮灯小时

判读：
- 若单位亮灯时间能耗基本一致，不支持系统性功率异常升高。
- 若单位亮灯时间能耗明显抬升，再考虑系统性功率或计量异常。

### 5. 按亮灯时长变化分组汇总

按“亮灯分钟变化区间”分组，统计：
- 灯数
- 组内能耗增量

用途：
- 识别是否为全网普遍多亮约半小时、一小时等。
- 区分全局分布性变化与少数局部异常点。

### 6. 筛高值单灯，但注意优先级

优先筛：
- 亮灯分钟变化不大，但能耗激增的单灯

这类点更像：
- 计量异常
- 台账异常
- 实际带载异常

同时要说明：少数高值单灯可能放大峰值，但未必是全局抬升主因。

### 7. 用上线率、亮灯率、报警做排除

若上线率、亮灯率、报警情况没有支持故障解释，应明确写出：
- 不支持“系统故障导致高能耗”的解释

这样可以避免把正常控制时长变化误判为设备异常。

### 8. 给后续排查两条线

通常优先：
- 查异常日前后开关灯日志、控制策略、时长变化原因
- 查异常日高能耗单灯明细，重点看“时长没明显增加但能耗跳升”的点

## 输出格式

建议顺序：
1. 一句话结论：主因是时长还是非时长因素
2. 关键证据 3~5 条
3. 增量拆分结果
4. 全网还是局部异常的判断
5. 重点异常单灯
6. 后续排查建议

# 节能率分析

## 固定取数口径

- 默认对象：全系统日报。
- 默认范围：截至查询当日的前7个已完成自然日。
- 固定查询脚本：服务内固定查询（不执行脚本）。
- 固定返回：日期、理论能耗、实际能耗、系统记录节能量、系统记录节能率，以及按能耗差计算的节电量、节能率。

## 执行

1. 标准全系统近7日请求，由服务使用已固化的只读查询；**不进行案例检索、示例检索、Schema 扫描或临时生成 SQL**。
2. 使用受控只读查询入口执行固定查询。
3. **将实际查询结果交由 LLM 分析**：由 LLM 判断综合节能率、逐日趋势、波动、系统指标一致性、可确认结论、待核查事项及处理建议；不得用脚本模板替代业务分析。
4. 目标节能率仅在用户或系统明确提供时比较；未提供时说明暂无法判断目标差距。
5. 用户要求按道路、工区、RTU、指定特殊日期、改变公式或追溯策略执行原因时，固定口径不适用，回退到 `sql-safe-query` 标准确认流程。

## 输出约束

- 先给 LLM 基于实际数据形成的综合结论，再列逐日趋势与核查建议。
- 系统记录节能率为零、但理论与实际能耗差额存在时，只能判定为“系统指标一致性异常”；具体原因须另行核查。
- 未取得目标值时，不猜测目标或达成状态。
- 默认不展示 SQL 和内部执行过程；用户明确要求时再提供必要技术细节。
